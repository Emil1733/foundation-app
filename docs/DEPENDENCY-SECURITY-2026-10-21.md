# Dependency security patches — October 21, 2026

## Scope and baseline

Separate follow-up to the human lead-integrity rollout. The initial `npm audit --omit=dev` reported 17 vulnerable production dependency entries: 3 critical, 8 high and 6 moderate. These are package/advisory findings, not evidence of exploitation or a claim that every affected API is used by this application.

Critical paths were Next.js 16.1.4, jsPDF 4.0.0 and `proxy-addr` 2.0.7 through MCP SDK → Express. The local MCP server uses stdio rather than an Express HTTP listener, but its installed transitive dependencies still need patching. Several Next.js advisories concern configurations/platforms not used by the production Vercel deployment; that does not justify retaining the old release.

## Update strategy

- Pin Next.js and its ESLint configuration together at 16.4.2, preserving the existing major version.
- Pin jsPDF at 4.2.1 and MCP SDK at 1.32.1, retaining their existing major versions and public import paths.
- Refresh vulnerable transitive packages within compatible declared ranges using `npm audit fix --ignore-scripts`, never `--force`. Review the resulting lockfile and rerun installation/build tests.
- Do not change provider claims, page copy, SEO cohorts, consent, form fields, database privileges or environment credentials in this batch.

Primary references: [Next.js release](https://github.com/vercel/next.js/releases/tag/v16.4.2), [jsPDF releases](https://github.com/parallax/jsPDF/releases), [MCP SDK releases](https://github.com/modelcontextprotocol/typescript-sdk/releases), and [proxy-addr advisory](https://github.com/advisories/GHSA-jqcg-44mw-7w3h). npm registry metadata and the audit response establish the installed versions and affected dependency ranges at verification time.

### Compatibility defect caught before publication

The first patched build compiled and passed the initial unit tests, but a real local HTTP request for city JSON returned 400. The direct `?slug=cedar-park-tx` API returned 200, and adding that query to the public city URL also returned 200. Inspection of installed Next.js 16.4.2's `base-server.js` confirmed it resets the handler request URL to the original URL/search string; a slug added only to the internal rewrite query was therefore unavailable to the handler. This is a verified compatibility failure, not a database record problem.

The proxy now rewrites to `/api/agent/soil-data/[slug]`. Both the dynamic and original query endpoints share one GET handler. It reads the resolved route parameter first and retains query compatibility for the original direct endpoint. The route parameter overrides conflicting caller query values. Existing slug validation, soil-report suffix normalization, anonymous public-data client, recognized-agent analytics behavior, and private/no-store headers are unchanged. No new privileged public-data read or database migration.

`scripts/test-agent-representations.cjs` verifies path/query precedence, invalid slug rejection before database access, suffix normalization, public-client-only reads, Markdown/JSON cache headers and missing/upstream-error statuses without network calls. `node scripts/test-http-routing.mjs http://localhost:3011` tests the actual production server, and accepts `https://foundationrisk.org` for the post-deployment read-only check. This HTTP test is not run in credential-free CI; CI runs the isolated proxy and handler checks instead.

Real concurrent lead writes remain limited to CI's disposable PostgreSQL service. Do not submit a synthetic production lead to validate a dependency update. A clean package audit is a point-in-time result, not a guarantee against future vulnerabilities or unresolved application-level risks.
